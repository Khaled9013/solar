# Solar

A self-hosted Django workspace for Codex, Claude Code, OpenAI-compatible models, scheduled tasks, agent roles, skills, file previews, an administrator PowerShell terminal, and an on-demand remote desktop.

Solar runs on the PC that does the work. Open its HTTPS address from another device to manage your sessions. It uses Python, Django, HTML, CSS, and JavaScript; there is no Node build step or external frontend CDN.

## Start

Install [uv](https://docs.astral.sh/uv/getting-started/installation/), then run these commands from this directory in a **normal terminal under your own OS account**:

```sh
uv run solar
```

The first run resolves the Python environment, migrates the database, creates a private storage key, generates a temporary administrator and HTTPS certificate, and starts the web server and task worker. It also installs a pinned CAD viewer runtime (about 7.6 MB) for STEP/IGES previews. Python 3.12 or newer is required; uv can provision Python if needed. Initial dependency installation needs internet access. If the CAD download fails, the rest of Solar still starts and CAD previews explain how to retry.

Open **https://localhost:5557** on this PC, or **https://YOUR-PC-IP:5557** from your other device. Solar binds IPv4 `0.0.0.0` and IPv6 `::` by default. If port 5557 is occupied, startup fails with an explanation; choose another port in `solar.conf`.

In a second local terminal, display the generated credentials:

```sh
uv run solar credentials
```

The bootstrap username is `admin`; its password is randomly generated for your installation. Both bootstrap values are encrypted in `solar.conf`, and the password is also stored as an Argon2 hash. Sign-in requires replacing the temporary password. The recoverable temporary password is then removed from the configuration. A new shared default password is never introduced.

Solar prints the HTTPS certificate fingerprint at startup. Trust your installation's certificate on each client device, or configure a certificate issued by your own CA. Check the fingerprint before trusting a self-signed certificate. Browser certificate handling varies, especially for WebSockets and mobile clients.

Use a private LAN or a VPN connecting your devices for remote access. Solar does not create firewall rules, port forwarding, a public tunnel, or a cloud account. You must allow the configured port on the appropriate private network if your firewall blocks it.

To replace the bootstrap account, create your own administrator in **Users**, sign in as that administrator, and remove the original account. Account removal disables sign-in, host and desktop access, runs, and schedules; it retains existing encrypted records. An administrator cannot remove their currently signed-in account or the last active administrator.

## Configuration and local commands

`solar.example.conf` contains all defaults and can be copied to `solar.conf` before startup. An installation-specific `solar.conf` is already supplied in this workspace without credentials; credentials are generated by the first successful initialization. The local file, databases, keys, accounts, logs, uploads, and original sample folders are excluded by `.gitignore`.

Important settings:

| Setting | Default | Meaning |
| --- | --- | --- |
| `server.hosts` | `0.0.0.0`, `::` | IP addresses to bind |
| `server.port` | `5557` | Web and WebSocket port |
| `server.allowed_hosts` | empty | Extra DNS names; local interface addresses are discovered at startup |
| `server.tls` | `true` | HTTPS; disabling it is permitted only on loopback |
| `server.certificate`, `private_key` | empty | Optional existing certificate and key paths |
| `storage.directory` | `.solar` | Private state, relative to the installation root |
| `storage.max_file_mb` | `50` | Maximum individual uploaded or collected file |
| `storage.quota_mb` | `2048` | File quota per user |
| `storage.export_mb` | `250` | Maximum file bytes in a ZIP export |
| `execution.max_workers` | `3` | Concurrent runs |
| `execution.timeout_seconds` | `3600` | Maximum run duration |
| `execution.native_idle_seconds` | `1800` | Native terminal idle timeout |
| `desktop.enabled` | `true` | Availability of the desktop feature; capture remains off until Run |
| `providers.allowed_api_origins` | local Ollama, local LM Studio, OpenAI | Exact origins permitted for outbound model API requests |

Restart after changing configuration. If your PC gets a new network address, restart Solar to refresh the allowed host list. To regenerate the built-in certificate's address list, stop Solar and move its old `server.crt` and `server.key` out of `.solar/tls/`, then restart.

```sh
uv run solar init
uv run solar check
uv run solar viewer-assets
uv run solar credentials
uv run solar reset-password --username YOUR_USERNAME
uv run solar --home /path/to/installation --config /path/to/solar.conf
```

Local password recovery generates a new temporary password, invalidates existing authenticated sessions, and requires a change at sign-in. It does not print existing personal passwords.

Use one Solar process per data directory. `uv run solar` owns the scheduler and worker as well as the ASGI server. Running only Django's development server or starting multiple independent ASGI workers is not a supported deployment.

## Providers and chat modes

Each user has a private provider list. API secrets are write-only through the UI and encrypted in storage.

| Provider | Setup | Interaction |
| --- | --- | --- |
| Codex | Install `codex` and authenticate it on the host, or configure a provider API key | Structured chat and native CLI terminal |
| Claude Code | Install `claude` and authenticate it on the host, or configure an Anthropic API key | Structured chat and native CLI terminal |
| Ollama | Run its compatible API; default base URL `http://127.0.0.1:11434/v1` | Streaming chat and supported file tools |
| LM Studio | Enable its compatible server; default base URL `http://127.0.0.1:1234/v1` | Streaming chat and supported file tools |
| Another model server | Add its exact origin to the local config and enter its `/v1` base URL | OpenAI-compatible chat completions |

Solar does not bundle model weights, provider subscriptions, or the Codex/Claude executables. Provider-side model access, reasoning levels, API schemas, and tool support still apply. API models must have an explicit model ID; the **Models** action queries the configured server. Disable tool calling, vision, or `reasoning_effort` when your model server does not support that feature.

The Codex integration uses a private file-backed credential store for each workspace. A configured API key is supplied to the CLI's supported login command over stdin; it is never included in process arguments. Host-login reuse requires a file-based auth cache. If your existing login is held only in an OS keyring, use the native login flow or configure a key instead. See [Codex authentication and credential storage](https://learn.chatgpt.com/docs/auth).

**Structured chat** shows streaming replies, tool activity, files, and run status. Codex and Claude run in the selected project or a private per-chat workspace. Their conversation state is encrypted between turns and restored to resume the same provider session. An initial turn receives bounded existing Solar history; subsequent turns send only the latest request. OpenAI-compatible models receive bounded Solar history, confined file tools, and selected delegation tools. Ordinary accounts have no host command tool.

For a trusted account with **host execution** permission, an API agent with **workspace write** and **allow shell tools** can also use `run_command`. This lets a capable local model invoke installed compilers, test runners, MCU tools, and other programs using an argument array. Commands run in the chat workspace, have 60-second default/300-second maximum timeouts and a 64 KB output cap, and import their generated files afterward. Skill resources are materialized for the command. A child role cannot gain command access missing from its parent. These commands run with the PC account's privileges and are not an OS sandbox; the network-tools checkbox does not firewall shell programs.

**Native terminal** runs the installed Codex or Claude interactive interface inside the browser, with keyboard input, terminal resizing, provider approval prompts, and the slash commands supported by that CLI version. Use this mode for provider-specific workflows that the structured UI does not implement. It is a real CLI integration, not a reproduction of every feature in the separate Codex desktop application. Terminal disconnect does not immediately terminate the run; reopen it from the same chat before its idle timeout. Stop from the chat or Activity page when finished. Native provider state is encrypted between runs and restored for resume.

The web composer supports:

```text
/model MODEL_ID
/effort minimal|low|medium|high|xhigh|max|ultra
/permissions read-only|workspace-write|danger-full-access
/approvals default|on-request|never|auto-review
/workspace PROJECT_NAME_OR_ID|none
/agent AGENT_NAME_OR_ID|none
/skill SKILL_NAME_OR_ID
/skills
/status
/stop
/plan TASK
/review
/compact
/native
/help
```

Effort values are validated for the provider; model-specific support can be narrower. `/skill` toggles a selected skill. `/plan`, `/review`, and `/compact` in the web composer submit guided prompts. `/compact` creates a summary; it does not delete history or perform the provider's native compaction operation. Use the native terminal for the provider's own command semantics.

Type `/` to open command autocomplete. Up/Down selects an item; Tab or Enter completes it; Escape closes the menu. Commands that take arguments then suggest models, efforts, permissions, agents, skills, or projects. Selecting a suggestion does not submit the message; press Enter after completing it. Shift+Enter inserts a newline.

Session settings expose the actual sandbox and approval policy. `default` means never ask in structured mode and ask when needed in native mode. Explicit `on-request` opens an interactive terminal so you can answer provider prompts. `never` keeps the selected sandbox and denies actions that need escalation. Codex `auto-review` uses its automatic approval review and requires workspace-write. Full host access removes the provider sandbox and requires a trusted host account; a selected agent role can still narrow permissions. Shell and network toggles intersect with the role's settings. Native commands may alter permissions for that live provider session; Solar reapplies the saved web settings on the next launch.

Codex `max` and `ultra` effort are available when supported by the chosen model. The picker reads the installed Codex model catalog, and the model field also accepts an explicit ID. Windows Codex sessions default to the unelevated sandbox; selecting elevated requires the CLI's Windows sandbox setup to have been completed on the PC. Native terminals support resizing, font controls and an expanded view.

## Projects on the remote PC

With host execution permission, click **Browse folders…** beside **Workspace / output folder** in the new-session window, session settings, or automation form. A separate folder picker opens while keeping your draft settings intact. Navigate drives and subfolders, or paste an absolute path and click **Go**, then **Use this folder**. To create a directory inside the displayed folder, click **New folder → Create & use folder**. Solar registers and selects the folder automatically; you do not need to visit Projects first. Cancel leaves the previous selection and draft untouched. Existing registrations are reused.

If the session is read only, click **Enable workspace writes** beneath the selected path to allow output files; agent-role restrictions still apply. Requested work and deliverables go to the selected folder, while chat attachments and history remain separate. You can also manage registrations under **Projects → Add project**, select a saved folder from the workspace dropdown, or use `/workspace`. The session file pane has separate **Chat files** and **Project** tabs; the project tab browses and downloads live files and uploads new files or folders without overwriting existing files.

Agents run with the real project as their working directory. Project files stay in place; Solar never replaces project `AGENTS.md`, `CLAUDE.md`, or provider configuration with its generated instructions. Chat attachments, outputs and provider state use a separate private runtime and encrypted vault. Cleanup removes that runtime, never the linked project. The same physical project is locked across Solar runs to avoid concurrent edits; uploads wait until the active project run stops. External editors are outside this lock.

Project registrations are private to their owner and encrypted. Existing project files remain normal files on the PC and are not encrypted or backed up by Solar. Removing a registration does not remove the directory. Remote network shares, links/junctions and Solar private storage cannot be selected through the project browser. API models use bounded `list_workspace`, `read_workspace`, and, when permitted, `write_workspace` tools for linked projects.

## Files and conversation storage

Each chat has this virtual layout in its file pane and ZIP export:

```text
chat_YYYY-MM-DD_UUID/
  chat_history.txt
  references.csv
  user/
    files/
    images/
    zip_files/
  codex/
    files/
    images/
    zip_files/
    agents/
```

The `codex/` name matches the requested layout and is used for outputs from all providers. Folder uploads and drag-and-drop preserve relative paths. Standalone raster images and ZIPs go into their matching input categories. Download an individual file, a folder ZIP, the whole chat, its history, or its reference CSV. Raster previews from the vault are decoded and re-encoded. HTML and SVG can be inspected as source text; their markup is never executed. ZIP extraction rejects traversal, links, duplicate names, and excessive expansion.

Click a filename in **Chat files** or **Project** to open its preview. The download arrow still downloads the original file. Relative file links in agent messages also open previews when the file can be located in the session or linked project.

| Format | Preview |
| --- | --- |
| PDF | Pages, page number, zoom, fit width; rendered locally with PDF.js |
| Markdown (`.md`, `.markdown`, `.mdown`) | Headings, lists, tables, code, links, and a source toggle |
| STEP/STP, IGES/IGS, BREP/BRP | CAD tessellation with orbit, pan, zoom, standard views and wireframe |
| STL, OBJ, PLY, GLB, glTF | Mesh or point preview with the same 3D controls |
| Raster images and common text/code files | Image or source preview |
| Other formats | Download remains available |

Use **Expand** inside the preview for more space. In the right file panel, **Expand** widens the panel and **Collapse** hides it; **Files** in the chat header reopens it. The top-left navigation button folds the left sidebar. Panel preferences are saved per account in that browser.

Previews read through the existing authenticated file APIs and run in your browser. Files are not sent to an online viewer. Markdown HTML is displayed as text; remote images are not fetched. Model textures and animations are omitted, and Draco/Meshopt-compressed glTF models need to be exported as uncompressed GLB or STL. Keep glTF `.bin` resources beside the model when uploading. Relative links and resources remain inside the same chat/project. Text previews are limited to 2 MB; PDF/3D previews to 50 MB, with additional geometry and processing limits. STEP/IGES dimensions are shown in millimeters; BREP and mesh dimensions use model units.

The CAD runtime is the only viewer component downloaded at startup. Its exact size and Git object hash are checked before installation; once installed, the viewer works offline. To retry, stop Solar, run **`uv run solar viewer-assets`**, and restart **`uv run solar`**. An offline installation can copy `occt-import-js.wasm` from a verified installation into `solar/static/vendor/`; startup verifies it again. Library versions, source and licenses are listed in [vendor/PROVENANCE.txt](solar/static/vendor/PROVENANCE.txt).

Physical chat directories are under `.solar/chats/USER_UUID/`. Content, history, logical names, and provider state are encrypted; physical files use opaque IDs and revision IDs. The plain logical tree appears in the authenticated UI, exports, and temporary execution workspace. Directly browsing the encrypted vault will not show readable uploaded filenames or text.

While a host CLI or authorized API command is running, `.solar/runtime/CHAT_UUID/` contains plaintext that the provider or program needs to read. On completion or cancellation, regular files are imported into the encrypted vault and the temporary directory is removed. Outputs become downloadable after collection. Links, dependency caches, provider homes, and internal instructions are excluded. Failed collection retains the protected workspace for local recovery, with an error in the chat. Restart attempts recovery after an interruption. Exports and files downloaded to a client are plaintext copies.

Default limits include 200 files per upload batch, 100 MB total HTTP upload size, 50 MB per file, 2 GB file storage per user, 2,000 collected workspace files, 20 active or queued runs per user, and 50 MB native provider state. Large projects should exclude dependencies/build caches or use ZIPs within the configured limits. File quotas do not cover all database history or operating-system disk usage.

## Agents, skills, and automations

Create named roles with instructions, read/write permissions, optional host shell/network tools, selected skills, and allowed delegate roles. Choose the role for a chat or scheduled task. In the API adapter, delegation is explicitly allowlisted, cycle checked, depth limited, and inherits read-only restrictions. Delegate reports are saved under `codex/agents/`.

For native CLIs, Solar writes selected role definitions and tool/sandbox settings for the provider. Provider-native permissions enforce these settings; they are not an OS isolation boundary. Codex may also offer built-in roles, and native command behavior depends on the installed CLI. Claude delegates are one level deep in this integration. API delegation supports up to three nested levels. Host execution is for trusted operators.

Create a Markdown skill or import one `SKILL.md` with optional ZIP resources. Importing stores data without executing it. Enabling a skill exposes its instructions and resources to the chosen provider. Hardware debugging, 3D software, drivers, and other specialized tools must be installed separately on the host and require the appropriate role permissions. Solar does not pretend a written skill installs those external capabilities.

Automations support one-time tasks, intervals, and five-field cron expressions in an IANA timezone. For “every three days for the next three months,” choose **Interval**, every **3 Days**, and duration **3 months**. An optional maximum count limits occurrences. Each task has one continuing chat: every occurrence appends a new run, retaining files, history and the provider conversation. **Open session** opens that chat. The schedule page shows individual run history and can pause or resume the task. Interactive approval is unavailable for unattended tasks; use never ask or Codex automatic review.

Upgrading adopts each existing task's most recent chat and preserves older chats. Changes to the automation's execution settings and its chat's settings are synchronized. Archiving an automation chat pauses its task. A manual run in that chat also prevents overlapping scheduled work. A saved provider conversation cannot be moved to a different provider; create a separate task for that change.

Solar and the PC must be running. After downtime, missed intervals coalesce into one occurrence; schedules do not replay an unlimited backlog or overlap themselves. Cron handles skipped and repeated daylight-saving times. End dates and run counts stop future launches; they do not forcibly stop a run already in progress. The app does not wake a sleeping PC.

## Administrator PowerShell

Only administrators see **PowerShell** in the navigation. The administrator must also have **Trusted host execution** enabled under Users. Opening the page does not start a process: press **Start PowerShell**. You can type commands, resize, change font size, expand the terminal, reconnect after a dropped connection, and press **Stop** to end it.

This is a real host terminal running as the OS account that launched Solar, starting in that account's home directory. It has that account's filesystem and command permissions; chat sandbox and agent-role settings do not restrict this terminal. On Windows it uses PowerShell 7 when installed, otherwise Windows PowerShell. Other systems prefer `pwsh`, then the installed shell.

Each administrator can have one running terminal, bound to the browser's sign-in session. Navigating away disconnects the view and lets you reconnect. Stop, logout, password change, account/host-access revocation, sign-in expiry, the configured idle timeout, or the run duration limit ends the process. The server retains up to 1 MB of output in memory for reconnecting; it does not save a Solar terminal transcript. Shell tools can maintain their own host history and files. Closing a browser tab is not Stop. The time limits use `execution.native_idle_seconds` and `execution.timeout_seconds`.

## Remote desktop

The desktop page takes no screenshot until an authorized user presses **Run**. Choose the primary display or all displays, then enable **Keyboard & mouse** for control. It supports pointer movement, dragging, clicks, scroll, common shortcuts, Unicode text entry, and fullscreen viewing. Screen frames travel over an authenticated WebSocket and are not saved by Solar.

Only one browser session may hold the desktop lease. Disconnect, logout, Stop, permission revocation, an idle timeout, or the maximum session duration ends capture. Lost pointer capture releases held mouse buttons. Default stream quality is 4 FPS, at most 1600 pixels wide: this is a lightweight remote-control feature, not a video-call-quality RDP replacement.

Solar must run in an unlocked interactive desktop session. Windows secure desktops/UAC/sign-in screens are not controllable. Linux display-server support and macOS screen/input permissions depend on the OS and installed capture/input libraries; these platforms have not been exercised in this workspace.

## Privacy, backup, and maintenance

Read [SECURITY.md](SECURITY.md) before granting host or desktop access. Users are isolated through authenticated, owner-filtered application APIs. This encryption protects stored content, but it is not end-to-end encryption and cannot hide data from the host operator who possesses the master key. Administrators can reset passwords, which is an account-takeover capability even though they cannot directly fetch another user's chat through the API.

Stop Solar before taking a consistent backup of **both `solar.conf` and the complete `.solar/` directory**. Protect that backup as a secret: it contains the master key, encrypted data, password hashes, and provider credentials. Losing `.solar/master.key` makes existing encrypted data unrecoverable. Do not regenerate it over an existing database. Restore the same configuration, data, and key together, then start as the OS account that owns the files. File permissions may need to be reapplied after moving to another system.

Commit source code and `uv.lock`, never your local environment or data. The lockfile supplied with this workspace is retained. To update dependencies in a normal network-enabled environment, back up, run `uv lock --upgrade`, `uv sync`, and the tests, then restart. Stop the running server before restarting with `uv run solar`; startup applies pending database migrations automatically. Refresh browser tabs after the restart.
